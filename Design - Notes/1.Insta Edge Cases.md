Instagram Edge Cases — Controls & Patterns

## Edge Case 1 — Race: multiple Save clicks (bio/profile)
- Client-side controls:
  - Disable or debounce the Save button while mutation in-flight.
  - Optimistic update via `onMutate`; store previous state for rollback.
  - Attach an idempotency/request-id and optionally cancel or coalesce duplicate requests (AbortController). `queryCient.cancelQueries({key:..})`
- Server-side controls:
  - Idempotency key handling to ignore duplicates.
  - Optimistic concurrency (version/ETag) or merge/upsert semantics.
- React Query pattern:
  - `onMutate`: cancel queries  `queryCient.cancelQueries({key:..})`, snapshot previous data, apply optimistic `setQueryData`.
  - `onError`: rollback using context.
  - `onSettled`: `invalidateQueries` to refresh authoritative state.

## Edge Case 2 — Crash / tab close immediately after starting a post
- Client-side controls:
  - Autosave drafts to IndexedDB frequently.
  - Persist pending uploads/mutations to an IndexedDB-backed queue.
  - Use `beforeunload` + `navigator.sendBeacon` to persist small state/queue entries.
  - Show explicit "pending" state and a Resume UI when app restarts.
- Server-side controls:
  - Support resumable/chunked uploads or draft endpoints to accept partial work.
  - Accept idempotent retry attempts.
- React Query pattern:
  - Persist query cache with `persistQueryClient` for UI state.
  - When starting a mutation, enqueue to IDB if offline or on unload; process queue on startup/online.
  - Keep optimistic UI marked as pending until confirmed by server; reconcile on success/failure.

## Edge Case 3 — Offline → Online resync
- Client-side controls:
  - Queue mutations (with idempotencyKey, timestamp, clientSeq) in IndexedDB.
  - Processor that runs on `online` event or Service Worker Background Sync to replay queue sequentially/controlled-parallel.
  - Exponential backoff and retry counts; BroadcastChannel/localStorage events to coordinate across tabs.
  - UI: show pending indicators, retry status, and conflict prompts if needed.
- Server-side controls:
  - Idempotency handling and conflict-resolution endpoints (merge, accept-last-write-with-version, or explicit conflict API).
  - Return clear error codes for conflicts vs transient failures.
- React Query pattern:
  - Use a wrapper hook that enqueues when offline and executes immediately when online.
  - Use `onMutate` for optimistic UI, persist the optimistic change if queued, then reconcile on server response.

## Edge Case 4 — Optimistic update fails or tab closes mid-optimistic update
- Client-side controls:
  - Keep rollback `context` from `onMutate` to restore state on error.
  - Persist pending optimistic mutations to IDB so they survive tab close; display a persistent "pending" badge.
  - Listen to `visibilitychange` / `beforeunload` to persist state; use SW sync where possible.
- Server-side controls:
  - Return explicit validation/conflict responses; support compensating actions if needed.
  - Provide final authoritative state on success for reconciliation.
- React Query pattern: 
  - `onMutate` returns context; `onError` uses it to rollback; `onSettled` invalidates authoritative queries.
  - When using a persisted queue, correlate mutation IDs with query cache and update cache on confirmation.

## Tools & infra to mention
- Persistence: `idb` / `localforage` for IndexedDB, `@tanstack/react-query-persist-client` for cache.
- Background: Service Worker + Background Sync API (where available), `navigator.sendBeacon` for small flushes.
- Cross-tab: `BroadcastChannel` or `storage` events.
- Server patterns: idempotency keys, ETag/versioning, resumable uploads (tus), merge/conflict API.
